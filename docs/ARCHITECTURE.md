# Kageha Architecture

This document describes the current architecture of Kageha: what exists, what is
integrated into production execution paths, and what remains experimental. It exists to
correct stale claims made in earlier point-in-time research notes (see
`docs/research/AGENT_ENGINEERING_PATTERNS.md`) that verifier agents, specs, tracing, and
replay were entirely absent — several of those gaps have since been closed, and this
document is the maintained source of truth going forward.

## The contract → evidence → verification → repair lifecycle

For a turn where a `TaskContract` exists, the reliability spine follows this sequence:

1. **Compile** — `ContractCompiler.compile()` classifies the turn (trivial/lookup turns
   skip this entirely), runs the `DeterministicExtractor` against the request text, and
   optionally sends the draft to the planner model via `SemanticCompletionService` for
   additive completion. Planner failures fall back to the deterministic draft without
   blocking the turn.
2. **Persist** — the resulting `TaskContract` is stored via `RuntimeStore.put_task_contract()`,
   keyed by `(session_id, turn_id)`, so it survives resume and replay.
3. **Execute** — the existing `LoopController` plan/act loop runs unchanged; a contract does
   not alter tool dispatch, approvals, or the chat experience.
4. **Verify** — `VerificationEngine.verify()` runs each `SuccessCriterion` through three
   fixed-order stages — deterministic postcondition, artifact check, semantic judgment — and
   assembles a `VerificationReport`. A deterministic failure always wins regardless of the
   semantic stage's result.
5. **Record evidence** — every stage that produces proof appends an `EvidenceRecord` to the
   `EvidenceLedger`, which redacts secrets before persisting and marks evidence from a prior
   turn as stale unless explicitly reconfirmed.
6. **Report** — `RunResult.report` carries the final `VerificationReport`; `RunResult.validated`
   is derived from `report.success`, which requires every *required* criterion to pass.
   Optional criteria may fail without excluding the turn from success.

## Qualification commands

- **Core_Qualification_Command** — a fast subset of checks for quick local iteration
  (`scripts/qualify_core.sh`).
- **Full_Qualification_Command** — lint, type checking, Python tests, and frontend tests
  together (`scripts/qualify.sh`). Intended to run noninteractively; any test genuinely
  requiring live provider/UI interaction is marked explicitly rather than allowed to prompt
  implicitly (see `tests/test_live_providers.py` and the stdin-guard fixture in `conftest.py`).

### Remaining pre-existing test failures blocking the qualification gate

These are **not** caused by the reliability spine and were failing before this work.
They must be resolved before either qualification command can go green:

1. `test_computer_regression.py` (3 failures) — a **test-isolation bug**: all 14 tests
   in that file pass when run in isolation and only fail during full-suite runs,
   indicating order-dependent global state leaking between driver/approval mocks.
2. `test_hitl.py::test_cli_approver_suggest` — `cli_approver` returns empty `feedback`
   for a `"s <suggestion>"` response; needs a behavioral decision about suggest-parsing
   in `harness/approvals.py`.
3. `test_design_save.py::test_controller_rereads_plan_md_on_approve` — plan-reload-on-approve
   does not surface the edited step into `task_state.stages`.
4. `test_chat_progress.py::test_detailed_progress_shows_reasoning_and_todo_checks` — cosmetic;
   the assertion does not account for Rich's ANSI color codes in the rendered output.

**Bottom line: the reliability spine is implemented, wired into the live execution
path, and verified end-to-end against a real model. The formal release gate (REL-043)
is still uncertified — the full 90-run adversarial suite has not been executed, and
both qualification commands are blocked by 6 pre-existing test failures listed above.**

## Known limitations

- The mid-loop `VerificationEngine` gates approximate milestone scoping rather than
  implementing it literally. The design describes scoping a milestone check to that
  milestone's criteria, but no `PlanStage` → `SuccessCriterion` mapping exists in this
  codebase. Instead, mid-run gates verify whichever criteria the previous report did not
  mark `PASS`. This also serves as the post-repair re-check (a repair cycle's next gate
  only re-verifies previously-failing criteria).
- `verify_with_defects` (the pre-existing semantic verifier) is still called on every
  gate alongside the `VerificationEngine`, rather than being fully replaced by it. The
  engine's required-criteria failures are merged into the same
  `ValidationSnapshot.defects` list, so both feed one control path — but there are
  still two verification *producers*, not one. Fully retiring `verify_with_defects`
  would require the mid-loop restructuring noted above.
- Turns without a runtime journal (e.g. the eval harness's `controller_factory` path,
  or direct `LoopController` construction in tests) never compile a contract and fall
  back to the pre-existing `validate_result()` + semantic double-check in
  `AgentRuntime._execute`. This is intentional and verified: such turns behave exactly
  as they did before this milestone.
- `followup`-mode turns deliberately skip contract compilation to avoid adding planner
  latency to short chat replies.
- A required criterion whose every verification stage returns `skip_not_applicable`
  currently passes vacuously (no evidence proves it). Requirement 14.1's stricter
  "success requires accepted evidence" rule is not yet enforced at the engine level.
